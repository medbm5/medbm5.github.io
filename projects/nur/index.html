The 30-second version

A fintech MVP where the database enforces the rules.

NUR connects students who are short on tuition money with mosques that lend interest-free (qard hasan). A student enters the amount they need, the app combines several mosques' loan programs to cover it, and each mosque approves its part, pays the school directly and collects monthly repayments into its own Stripe account. NUR never holds the loan money. Every loan state change runs through Postgres functions under row-level security.

The problem

Interest-free money exists. Finding it is the hard part.

Muslim students who avoid interest-bearing loans have few options when Quebec's government aid (AFE) falls short. Some mosques do lend interest-free, but each one runs its own informal process. Students don't know which mosques still have budget, and a mosque has no simple way to review a request, pay a school and track repayments.

The client's spec called for one shared platform for four groups:

  • Students find and request funding in one place, then repay automatically.
  • Mosques get a request inbox, repayment schedules and automatic collection.
  • Partner organizations post jobs and volunteering opportunities.
  • The NUR team runs identity checks, a blacklist, a guarantee fund and finance reporting.

What I built

From "how much do you need?" to the last repayment.

Funding finder

The student types an amount. A pure TypeScript function searches the programs they're eligible for and builds combinations of up to 5 loans that cover the need within each program's limits and remaining budget, ranked by fewest loans, fewest mosques, then lowest monthly payment. The request is checked again in SQL before anything is saved.

Live loan timeline

Every loan follows a fixed state machine, from submitted through fees paid, funds sent and repaying to completed, with exits like denied or withdrawn. Each change is logged as an event, and the student's page updates live through Supabase Realtime the moment the mosque acts.

Mosque inbox & decision

Mosque staff see requests arrive live and open a deliberately minimal applicant folder: name, school, a reliability score, warning signals and the tuition invoice behind an audited 60-second link. Approve or deny in one click, with a reason.

Repayments that skip the middleman

The student pays an activation fee through Stripe Checkout, which also saves their card. A daily job then charges each due installment straight to the lending mosque's Stripe Connect account, one payment per loan. Failed charges start a grace period with reminders, then a restriction and a recovery case.

Trust & safety for lenders

Stripe Identity verifies students (NUR keeps only the result and a keyed hash of the document number, never ID images). A blacklist screens sign-ups, borrowing caps limit what a student owes ($500, or $2,000 with a guarantor who verifies and signs), and mosques track money deployed, outstanding and repaid, with CSV exports.

Trilingual & installable

Every one of the 3,016 interface strings exists in French, English and Arabic. Logical CSS makes the Arabic layout mirror completely, and a test fails the build on any missing translation or forbidden wording (like "interest"). It installs as a PWA, with student tools like a monthly budget page.

How it's built

The UI asks. Postgres decides.

Security lives in the database: every table has row-level security, status columns are locked by triggers, and a loan can only change state through SQL functions that check who's asking and whether the move is allowed.

The interesting parts

Bugs that only a fintech app can have.

01

A NULL that let anyone manage loan programs

Problem: permission checks used role in ('owner','reviewer'). For a non-member the role is NULL, and NULL in (...) is NULL, not false, so the "deny" branch never fired.

Fix: caught by a database test while building the loan state machine. All staff checks now go through one can_manage_mosque() helper that returns a real boolean.

02

Students could lift their own ban

Problem: the ban check read a column on the student's profile, and the student's "edit your own row" policy covered every column, that one included.

Fix: the check now reads a separate bans table, and a guard trigger lets only admins or server functions touch ban columns, with a new test file to prove it.

03

Paying several mosques without touching the money

Problem: a student with loans from several mosques owes each one separately, and the platform must not collect and redistribute funds.

Fix: due installments are grouped per loan and each becomes its own direct charge on that mosque's connected account, with an idempotency key per installment set and day. The webhook allocates payments to installments in order and is safe to receive twice.

04

Live updates that silently stopped

Problem: the timeline, inbox and notification bell re-created their Realtime channel on every render, under a fixed name, so the active listener could end up detached while events kept arriving. It only failed sometimes.

Fix: stable references for the router and translator, plus a unique channel name per component. The end-to-end test for the live timeline then passed reliably.

05

First-come spots under concurrency

Problem: the first 100 verified students get free Premium as "Pioneers". Two verifications at the same instant could take the same spot.

Fix: assignment takes a Postgres advisory lock and hands out the lowest free number. A later fix stopped demo and test accounts from holding real spots, after the client noticed the public counter showing 95 instead of 100.

06

Due dates that moved by a day

Problem: formatting a date-only value as a JavaScript Date shifted it by a day depending on the server's time zone. On a repayment schedule, that's a real money problem.

Fix: date-only values are treated as calendar dates at noon UTC, and the schedule is built the same way in SQL and in a TypeScript mirror, with unit tests for month ends and leftover cents.

Quality & security

Tested where the rules live.

  • Database tests: 49 pgTAP files with 914 assertions covering row-level isolation, every allowed and forbidden loan transition, and the money functions.
  • Unit tests: 238 Vitest tests in 54 files for the pure logic: combinations, schedules, fees, scores.
  • End-to-end: 49 Playwright spec files against a real Supabase project, including full journeys in French and Arabic, signed Stripe webhook events, accessibility (axe) and offline checks.
  • CI: GitHub Actions runs typecheck, lint with zero warnings, unit tests, build, Playwright and Lighthouse budgets (accessibility ≥ 0.95).
  • Security: two-factor login (TOTP) required for admins and mosque owners, strict security headers (CSP, HSTS), rate limits enforced in Postgres, private file storage with audited links, and account export and deletion for Quebec's Law 25.

How I worked

Client specs in, tested slices out.

I turned the client's requirements into a backlog of user stories with priorities and acceptance criteria, then a build plan of numbered slices. Each slice is one commit, and a progress log records what was done, every decision and every blocker.

  • Non-negotiables written down first: security in the database, state changes only through SQL functions, money in integer cents, settings stored as data, no hard-coded text, WCAG 2.2 AA.
  • Client feedback loops: three design passes, a public simulator, a new fee model and a 27-item requirements workbook. After the client's MVP spec arrived, I re-planned v2 as 18 new slices on top of v1.
  • Flagging, not guessing: when a request had legal impact, such as a fee that grows with the loan amount, I flagged it for Sharia-board and consumer-protection review instead of just shipping it.
  • AI as an assistant: I used Claude Code to write much of the code. I set the plan and the rules, and I reviewed and tested every slice before it was committed.

What I learned and what's next

What I learned

  • Putting authorization in Postgres makes it testable, and those tests found real holes that UI tests never would.
  • Payments stay correct when the webhook is the only writer and every handler is safe to run twice.
  • Right-to-left is cheap with logical CSS from day one, and expensive to retrofit.
  • A written decision log made the switch from the v1 plan to the client's v2 spec painless.

What's next

  • Ship v2 to production once the client signs off.
  • Turn on Stripe Connect for real so automatic repayments go live, plus Google sign-in and error monitoring.
  • Get student pages under the 180 kB JavaScript budget.
  • Legal pages are waiting on legal and Islamic finance review.
