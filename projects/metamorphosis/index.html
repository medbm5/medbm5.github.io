The 30-second version

The file change happens where the file already is.

Start dragging a file, tap Shift, Ctrl or Alt, and a ring of options opens under your cursor. Drop the file on a segment and the result is saved next to the original, which is never modified. It's a Rust and Tauri tray app for Windows and Linux with 87 operations across images, PDFs, video, audio, documents, archives and local AI tools, a matching morph CLI and a website. Everything runs offline, and CI enforces it.

  • 87operations, from PDF → PNG to blur faces

The problem

Small file chores shouldn't need a big app, or an upload.

Turning a PDF into images, compressing a photo under 1 MB, cropping a screenshot, pulling the audio out of a video: each usually means opening a heavy editor or uploading the file to some website.

The idea is inspired by Tangerine, a drag-to-convert app for Mac by Leap Studio (Metamorphosis isn't affiliated with it), and brings it to Windows and Linux as free software. The rules I set:

  • the original file is never touched; every result is a new file next to it,
  • nothing leaves the computer: no account, no upload, no tracking,
  • the ring only offers what makes sense for the file you're dragging,
  • and anything the ring can do, the command line can do too.

What I built

Three rings, 87 operations, zero windows to open.

Shift opens Convert, Ctrl opens Tools and Alt opens Actions. Tools that need input expand into a full editor.

The ring, mid-drag

Global input hooks (Windows low-level hooks, X11 XInput2) spot a drag plus a key tap and open a transparent, click-through ring at the cursor. Only operations valid for that file type appear, so a PDF gets PDF options and a video gets video options.

87 operations across file types

Image tools (compress to a target size, crop, annotate, add a background, collage, redact), PDF render, merge, organize and compress, FFmpeg video and audio tools, documents, slides, sheets and subtitles, and archives, including 7z and RAR extraction with zip-slip protection.

Editors when a tool needs input

Tools that need adjusting open an expanded window, like this crop editor with aspect presets and live output naming. The photo editor's WebGL2 preview is tested against the Rust export to stay within a mean colour difference (ΔE) of 2.

Actions on several files at once

Share, copy, move, copy the path, open a terminal there, or park files on the Float shelf to drop them somewhere later. Results can be chained by dragging the new file again, and a chain you use often becomes a recipe with its own segment.

Wayland mode

Wayland blocks global input on purpose, so instead of fighting it the app switches to a drop dock that expands into the ring when files are dragged onto it. It's pinned with gtk-layer-shell where available, summoned through the GlobalShortcuts portal, and you switch rings by hovering the tabs.

Settings, recipes & watch folders

Plain-language settings for keys, colour, file naming and which segments the ring shows, in English and French. User TOML recipes can wrap any local command, confined so they can only write their output file, and watch folders process new files automatically.

How it's built

One spec drives the ring, the editors and the CLI.

A Cargo workspace. The UI is static HTML and JS inside Tauri webviews, and all file work happens in Rust. Each operation declares what it accepts, outputs and needs in an OpSpec, which gives it a ring segment, an editor form and CLI flags for free.

Tauri 2 shell · tray, overlay ring, drop dock, editors

Fed by morph-input-watch: a platform-independent state machine over Windows hooks or X11 XInput2.

The interesting parts

Cross-platform desktop work is mostly edge cases.

01

Recipes that can only write their own output

Problem: user recipes run arbitrary local commands, and I didn't want to hand a script the whole disk.

Fix: each command runs in a fresh staging folder. On Windows it gets a low-integrity token and the folder a low mandatory label, so the system's no-write-up policy blocks writes anywhere else. On Linux a Landlock ruleset allows writes only under the staging folder. Tests try to write outside it and check the file never appears, on both OSes.

02

Drops that never arrived

Problem: the overlay window is created hidden and reused for speed, but the webview doesn't register its drop handler on hidden windows, so the drag that opened the ring couldn't land on it.

Fix: the app registers its own Windows IDropTarget once the window is shown. The ring's first frame was measured at roughly 19–115 ms.

03

Race conditions the first CI run caught

Problem: temp folders were named from the process ID plus the clock, so two jobs starting in the same tick shared one. Parallel LibreOffice conversions also shared a profile and exited silently.

Fix: a counter-based, exclusively created temp folder and a separate LibreOffice profile per call. The app runs jobs in parallel threads, so these would have been random failures for users.

04

Linux failures, reproduced in WSL

Problem: on GitHub's Ubuntu runners the AI tests aborted inside ONNX Runtime, every command recipe failed under Landlock, and the AppImage wouldn't bundle.

Fix: reproduced and verified in WSL: a newer ONNX Runtime for Linux with a new pinned checksum, Landlock rules that grant only the rights the ruleset handles, and a library path so the bundler finds FFmpeg's libraries. The Linux build went from failing to a released AppImage and .deb.

05

Never offer what will fail

Problem: the code assumed every Windows machine could decode HEIF and AVIF, but Windows Server and N editions don't ship the codecs.

Fix: decode a tiny AVIF once and cache the answer. The ring only shows an operation if it will actually work on that machine.

Local AI

Face, text and background detection, without a network.

Blur faces, redact text, OCR, background removal and a searchable-PDF builder run through ONNX Runtime with small open models: UltraFace for faces, PP-OCRv3 for text, u2netp for backgrounds. Inference only, no training.

  • Optional components: the models are downloaded on demand with pinned SHA-256 checksums, so the installer stays small.
  • Evaluated in tests: on NASA public-domain crew photos plus a synthetic text image, face recall and text-region recall must be at least 0.90, OCR must read the expected words, and redaction must black out every detected face.
  • Proven offline: CI runs the AI tests with the network switched off.

Quality & delivery

Green CI on two operating systems, installers on every tag.

  • 114 Rust tests: unit tests plus 12 integration files covering image, PDF, media, office and archive matrices, recipes, sandboxed commands and the AI tools.
  • UI suites: ring visual snapshots in Chromium and WebKit with a cross-engine diff under 1%, reduced motion and forced colours; a settings test with 13 checks; and an editor preview-vs-export parity test.
  • End to end on Windows: drives the real app, without simulating input, through recipe hot reload and watch folders.
  • CI: 6 GitHub Actions jobs on Windows and Ubuntu: fmt, clippy with warnings as errors, tests, the offline guard, the visual suites and the AI tests without network.
  • Releases: a tag builds an MSI, an NSIS setup, an AppImage, a .deb and CLI zips. The website is gated by Lighthouse, and the last run scored 100 for accessibility, best practices and SEO.
  • Privacy, enforced: a CI script fails the build if network code appears anywhere outside the updater crate.

How I worked

21 slices, each with a "done when".

Before any code, I planned the project as 21 slices (S0–S20), each with a scope and a "done when" condition, plus a feature audit and a design mockup. Each slice ended with a version tag.

  • Decisions: Tauri over Electron for a small app on native webviews, CLI-first engines, one OpSpec for ring, forms and flags, an offline guarantee checked in CI, optional heavy components instead of a big installer, and a drop dock on Wayland.
  • A testing rule: never simulate mouse or keyboard input on my own desktop after an early test interfered with my terminals. UI tests use headless browsers, logs and read-only window captures.
  • AI as an assistant: I used Claude Code to implement the plan slice by slice: code, tests, CI and docs. I set the direction and made the calls along the way.

What I learned and what's next

What I learned

  • A declarative operation spec pays off: one new operation gets a ring segment, a form and a CLI flag at once.
  • Cross-platform desktop work is mostly edge cases: hidden-window drop targets, DPI scaling, Landlock rules, library paths, codecs on Windows Server.
  • The first CI run on clean machines found bugs local testing hadn't.
  • Planning slices with "done when" checks up front made it practical to build something this large with an AI assistant, and to verify every step.

What's next
