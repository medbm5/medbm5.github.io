The 30-second version

A fintech MVP where the database enforces the rules.

NUR connects students short on tuition with mosques that lend interest-free. Each mosque approves its share, pays the school and collects repayments into its own Stripe account, so NUR never holds the money.

  • 7 daysto MVP
  • 914database assertions
  • 238unit tests
  • 3languages

The problem

Interest-free money exists. Finding it is the hard part.

Some mosques in Quebec lend interest-free, but each runs its own informal process. Students don't know who has budget, and mosques have no simple way to review, pay and track loans.

  • Students find funding in one place and repay automatically.
  • Mosques get a request inbox and automatic collection.
  • The NUR team handles identity checks and reporting.

What I built

From "how much do you need?" to the last repayment.

Funding finder

Type an amount and get combinations of up to 5 loans that cover it.

Live loan timeline

Each loan moves through fixed steps, and the student's page updates live.

Mosque inbox

Staff see a minimal applicant folder and approve or deny in one click.

Automatic repayments

A daily job charges each installment straight to the lending mosque's Stripe account.

Trust and safety

Identity checks without storing ID images, borrowing caps, and a portfolio dashboard for mosques.

Trilingual

French, English and Arabic, with the layout fully mirrored right-to-left.

The hard parts

Bugs only a fintech app can have.

01

A NULL that skipped a permission check

For non-members, NULL in (...) wasn't false, so the deny branch never fired. A database test caught it; one helper now returns a real boolean.

02

Students could lift their own ban

The ban lived on a row students could edit. It moved to its own table, guarded by a trigger.

03

Paying several mosques without touching the money

Each loan's installments become a separate direct charge to that mosque, and the webhook is safe to receive twice.

How I worked

Client specs in, tested slices out.

  • Turned the client's specs into user stories, then small slices, one commit each.
  • Tested where the rules live: pgTAP for the database, Vitest for logic, Playwright end to end.
  • Flagged legally sensitive requests for review instead of guessing.
  • Built with Claude Code as a coding assistant. I set the plan and reviewed every slice.

What I learned and what's next

What I learned

  • Authorization in Postgres is testable, and those tests found real holes.
  • Payments stay correct when the webhook is the only writer.
  • Right-to-left is cheap from day one and expensive later.
